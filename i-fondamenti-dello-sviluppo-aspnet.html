    4. I fondamenti dello sviluppo ASP.NET

    4.1. Il concetto di applicazione web ASP.NET

    4.1.1. Introduzione

    Un'applicazione web è un'applicazione che raggruppa vari documenti (HTML, codice .NET, immagini, suoni, ...). Questi documenti devono trovarsi nella stessa directory principale, chiamata radice dell'applicazione web. A questa radice è associato un percorso virtuale del server web. Abbiamo già incontrato il concetto di cartella virtuale per il server web Cassini. Questo concetto esiste anche per il server web IIS. Una differenza importante tra i due server è che, in un dato momento, IIS può avere un numero qualsiasi di cartelle virtuali, mentre il server web Cassini ne ha solo una, quella specificata al momento del suo avvio. Ciò significa che il server IIS può ospitare più applicazioni web contemporaneamente, mentre il server Cassini ne ospita solo una alla volta. Negli esempi precedenti, il server Cassini veniva sempre avviato con i parametri (<webroot>,/aspnet) che associavano la cartella virtuale /aspnet alla cartella fisica <webroot>. Il server web serviva quindi sempre la stessa applicazione web. Ciò non ci ha impedito di scrivere e testare pagine diverse e indipendenti all’interno di questa singola applicazione web. Ogni applicazione web dispone di risorse proprie che si trovano nella sua radice fisica <webroot>:

    • una cartella [bin] in cui è possibile inserire classi precompilate
    • un file [global.asax] che consente di inizializzare l’applicazione web nel suo complesso, nonché l’ambiente di esecuzione di ciascuno dei suoi utenti
    • un file [web.config] che consente di configurare il funzionamento dell’applicazione
    • un file [default.aspx] che funge da porta d'accesso all'applicazione
    • ...

    Non appena un'applicazione utilizza una di queste tre risorse, necessita di un percorso fisico e virtuale a sé stante. Non vi è infatti alcun motivo per cui due diverse applicazioni web debbano essere configurate allo stesso modo. Tutti i nostri esempi precedenti hanno potuto essere inseriti nella stessa applicazione (<webroot>,/aspnet) poiché non utilizzavano nessuna delle risorse sopra menzionate.

    Torniamo all’architettura MVC raccomandata all’inizio di questo capitolo per lo sviluppo di un’applicazione web:

    L’applicazione web è costituita dai file di classe (controller, classi di business, classi di accesso ai dati) e dai file di presentazione (documenti HTML, immagini, suoni, fogli di stile, ecc.). L'insieme di questi file sarà collocato in una stessa directory radice che chiameremo talvolta <application-path>. Questa directory radice sarà associata a un percorso virtuale <application-vpath>. L'associazione tra questo percorso virtuale e il percorso fisico avviene tramite la configurazione del server web. Abbiamo visto che per il server Cassini questa associazione avviene all'avvio del server. Ad esempio, in una finestra DOS, si avvierebbe Cassini con:

    webserver.exe /port:80 /path:<application-path> /vpath:<application-vpath>

    Nella cartella <application-path>, a seconda delle nostre esigenze, troveremo:

    • la cartella [bin] in cui inserire le classi precompilate (dll)
    • il file [global.asax] quando sarà necessario eseguire delle inizializzazioni, sia all’avvio dell’applicazione, sia all’avvio di una sessione utente
    • il file [web.config] quando sarà necessario configurare l’applicazione
    • il file [default.aspx] quando avremo bisogno di una pagina predefinita nell’applicazione

    Per rispettare questo concetto di applicazione web, gli esempi che seguiranno saranno tutti collocati in una cartella <application-path> specifica dell’applicazione, alla quale sarà associata una cartella virtuale <application-vpath>, poiché il server Cassini viene avviato in modo da collegare questi due parametri.

    4.1.2. Configurare un’applicazione web

    Se <application-path> è la radice di un'applicazione ASP.NET, è possibile utilizzare il file <application-path>\web.config per configurarla. Questo file è in formato XML. Ecco un esempio:

    <?xml version="1.0" encoding="UTF-8" ?>

<configuration>
  <appSettings>
    <add key="nom" value="tintin"/>
    <add key="age" value="27"/>
  </appSettings>   
</configuration>

    Si presti attenzione al fatto che i tag XML distinguono tra maiuscole e minuscole. Tutte le informazioni di configurazione devono essere racchiuse tra i tag <configuration> e </configuration>. Esistono numerose sezioni di configurazione utilizzabili. Qui ne presentiamo solo una, la sezione <appSettings>, che consente di inizializzare i dati con il tag <add>. La sintassi di questo tag è la seguente:

    <add key="identificateur" value="valeur"/>

    Quando il server Web avvia un'applicazione, verifica se in <application-path> è presente un file denominato web.config. In caso affermativo, lo legge e memorizza le relative informazioni in un oggetto di tipo [ConfigurationSettings], che sarà disponibile in tutte le pagine dell'applicazione fintanto che questa rimane attiva. La classe [ConfigurationSettings] dispone di un metodo statico [AppSettings]:

    Per ottenere il valore di una chiave C del file di configurazione, si scrive ConfigurationSettings.AppSettings("C"). Si ottiene una stringa di caratteri. Per utilizzare il file di configurazione precedente, creiamo una pagina [default.aspx]. Il codice VB del file [default.aspx.vb] sarà il seguente:

    
Imports System.Configuration

Public Class _default
    Inherits System.Web.UI.Page

    Protected nom As String
    Protected age As String

    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
        'si recuperano le informazioni di configurazione
        nom = ConfigurationSettings.AppSettings("nom")
        age = ConfigurationSettings.AppSettings("age")
    End Sub

End Class

    Si nota che, al caricamento della pagina, vengono recuperati i valori dei parametri di configurazione [nom] e [age]. Questi verranno visualizzati dal codice di presentazione di [default.aspx]:

    
<%@ Page src="default.aspx.vb" Language="vb" AutoEventWireup="false" Inherits="_default" %>
<html>
    <head>
        <title>Configuration</title>
    </head>
    <body>
        Nom :
        <% =nom %><br/>
        Age :
        <% =age %><br/>
    </body>
</html>

    4.1.3. Applicazione, Sessione, Contesto

    4.1.3.1. Il file global.asax

    Il codice del file [global.asax] viene sempre eseguito prima che la pagina richiesta dalla richiesta corrente venga caricata. Deve trovarsi nella radice <application-path> dell'applicazione. Se presente, il file [global.asax] viene utilizzato in diversi momenti dal server web:

    1. all’avvio o alla chiusura dell’applicazione web
    2. quando una sessione utente ha inizio o termina
    3. quando viene avviata una richiesta utente

    Come per le pagine .aspx, il file [global.asax] può essere scritto in diversi modi e, in particolare, separando il codice VB in una classe controller e nel codice di presentazione. Questa è la scelta predefinita dello strumento Visual Studio e qui faremo lo stesso. Normalmente non è prevista alcuna presentazione, poiché tale ruolo è affidato alle pagine .aspx. Il contenuto del file [global.asax] si riduce quindi a una direttiva che fa riferimento al file contenente il codice del controller:

    
<%@ Application src="Global.asax.vb" Inherits="Global" %>

    Si noti che la direttiva non è più [Page] ma [Application]. Il codice del controller [global.asax.vb] associato e generato dallo strumento Visual Studio è il seguente:

    
Imports System
Imports System.Web
Imports System.Web.SessionState

Public Class Global
    Inherits System.Web.HttpApplication

  Sub Application_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva all’avvio dell’applicazione
    End Sub

    Sub Session_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva all’avvio della sessione
    End Sub

    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva all'inizio di ogni richiesta
    End Sub

    Sub Application_AuthenticateRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva durante un tentativo di autenticazione dell'utente
    End Sub

    Sub Application_Error(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva quando si verifica un errore
    End Sub

    Sub Session_End(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva al termine della sessione
    End Sub

    Sub Application_End(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva quando l'applicazione viene chiusa
    End Sub

End Class

    Si noti che la classe del controller deriva dalla classe [HttpApplication]. Nel ciclo di vita di un'applicazione si verificano diversi eventi importanti. Questi vengono gestiti da procedure il cui schema è riportato sopra.

    • [Application_Start]: ricordiamo che un’applicazione web è “racchiusa” in un percorso virtuale. L’applicazione si avvia non appena una pagina situata in tale percorso virtuale viene richiesta da un client. Viene quindi eseguita la procedura [Application_Start]. Ciò avverrà una sola volta. In questa procedura si effettuerà ogni inizializzazione utile all’applicazione, come ad esempio la creazione di oggetti la cui durata corrisponde a quella dell’applicazione.
    • [Application-End]: viene eseguita al termine dell’applicazione. A ogni applicazione è associato un tempo di inattività, configurabile in [web.config], al termine del quale l’applicazione viene considerata terminata. È quindi il server web a prendere questa decisione in base alle impostazioni dell’applicazione. Il tempo di inattività di un’applicazione è definito come il periodo durante il quale nessun client ha effettuato una richiesta per una risorsa dell’applicazione.
    • [Session-Start]/[Session_End]: A ogni client è associata una sessione, a meno che l’applicazione non sia configurata come priva di sessione. Un client non è un utente davanti al proprio schermo. Se quest’ultimo ha aperto due browser per interagire con l’applicazione, rappresenta due client. Un cliente è identificato da un token di sessione che deve allegare a ciascuna delle sue richieste. Questo token di sessione è una stringa di caratteri generata in modo casuale dal server web ed è unico. Due clienti non possono avere lo stesso token di sessione. Questo token seguirà il cliente nel modo seguente:
      • il cliente che effettua la sua prima richiesta non invia alcun token di sessione. Il server web lo rileva e gliene assegna uno. Questo segna l’inizio della sessione e viene eseguita la procedura [Session_Start]. Ciò avverrà una sola volta.
      • il cliente effettua le richieste successive inviando il token che lo identifica. Ciò consentirà al server web di recuperare le informazioni associate a tale token. Ciò consentirà di tracciare le diverse richieste del cliente.
      • L’applicazione può mettere a disposizione del cliente un modulo per la chiusura della sessione. In questo caso, è il cliente stesso a richiedere la chiusura della propria sessione. Verrà eseguita la procedura [Session_End]. Ciò avverrà una sola volta.
      • Il cliente potrebbe non richiedere mai autonomamente la chiusura della propria sessione. In tal caso, dopo un certo periodo di inattività della sessione, anch’esso configurabile tramite [web.config], la sessione verrà chiusa dal server web. Verrà quindi eseguita la procedura [Session_End].
    • [Application_BeginRequest]: questa procedura viene eseguita non appena arriva una nuova richiesta. Viene quindi eseguita ad ogni richiesta proveniente da qualsiasi client. È un buon punto in cui esaminare la richiesta prima di inoltrarla alla pagina richiesta. Si può anche decidere di reindirizzarla verso un’altra pagina.
    • [Application_Error]: viene eseguita ogni volta che si verifica un errore non gestito esplicitamente dal codice del controller [global.asax.vb]. Qui è possibile reindirizzare la richiesta del cliente verso una pagina che spiega la causa dell’errore.

    Se nessuno di questi eventi deve essere gestito, il file [global.asax] può essere ignorato. È quanto è stato fatto con i primi esempi di questo capitolo.

    4.1.3.2. Esempio 1

    Sviluppiamo un’applicazione per comprendere meglio le tre fasi: l’avvio dell’applicazione, della sessione e di una richiesta del cliente. Il file [global.asax] sarà il seguente:

    <%@ Application src="Global.asax.vb" Inherits="global" %>

    Il file [global.asax.vb] associato sarà il seguente:

    
Imports System
Imports System.Web
Imports System.Web.SessionState

Public Class global
    Inherits System.Web.HttpApplication

    Sub Application_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Viene generato all'avvio dell'applicazione
        ' si registra l'ora
        Dim startApplication As String = Date.Now.ToString("T")
        ' viene memorizzata nel contesto dell'applicazione
        Application.Item("startApplication") = startApplication
    End Sub

    Sub Session_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Si attiva all'avvio della sessione
        ' si registra l'ora
        Dim startSession As String = Date.Now.ToString("T")
        ' la si inserisce nella sessione
        Session.Item("startSession") = startSession
    End Sub

    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' si registra l'ora
        Dim startRequest As String = Date.Now.ToString("T")
        ' la si inserisce nella sessione
        Context.Items("startRequest") = startRequest
    End Sub
End Class

    I punti salienti del codice sono i seguenti:

    • il server web mette a disposizione della classe [HttpApplication] di [global.asax.vb] un certo numero di oggetti:
      • Applicazione di tipo [HttpApplicationState] – rappresenta l’applicazione web – fornisce l’accesso a un dizionario di oggetti [Application.Item] accessibile a tutti i client dell’applicazione – consente la condivisione di informazioni tra diversi client – l’accesso simultaneo di più client agli stessi dati in lettura/scrittura richiede una sincronizzazione dei client.
      • Sessione di tipo [HttpSessionState] - rappresenta un cliente specifico - fornisce accesso a un dizionario di oggetti [Session.Item] accessibile a tutte le richieste di quel cliente - consentirà di memorizzare informazioni su un cliente che potranno essere recuperate nel corso delle sue richieste.
      • Richiesta di tipo [HttpRequest] - rappresenta la richiesta HTTP corrente del cliente
      • Risposta di tipo [HttpResponse]: rappresenta la risposta HTTP che il server sta generando per il cliente
      • Server di tipo [HttpServerUtility] - offre metodi di utilità, in particolare per reindirizzare la richiesta a una pagina diversa da quella inizialmente prevista.
      • Contesto di tipo [HttpContext] - questo oggetto viene ricreato ad ogni nuova richiesta, ma è condiviso da tutte le pagine coinvolte nell'elaborazione della richiesta - consente di trasmettere informazioni da una pagina all'altra durante l'elaborazione di una richiesta grazie al suo dizionario Items.
    • La procedura [Application_Start] registra l’inizio dell’applicazione in una variabile memorizzata in un dizionario accessibile a livello di applicazione
    • la procedura [Session_Start] registra l’inizio della sessione in una variabile memorizzata in un dizionario accessibile a livello di sessione
    • la procedura [Application_BeginRequest] registra l’inizio della richiesta in una variabile memorizzata in un dizionario accessibile a livello di richiesta (c.a.d disponibile per tutta la durata della sua elaborazione ma persa al termine della stessa)

    La pagina di destinazione sarà la seguente pagina [main.aspx]:

    
<%@ Page src="main.aspx.vb" Language="vb" AutoEventWireup="false" Inherits="main" %>
<html>
    <head>
        <title>global.asax</title>
    </head>
    <body>
        jeton de session  :
        <% =jeton %><br/>
        début Application  :
        <% =startApplication %><br/>
        début Session  :
        <% =startSession %><br/>
        début Requête  :
        <% =startRequest %><br/>        
    </body>
</html>

    Questa pagina di presentazione mostra i valori calcolati dal suo controller [main.aspx.vb]:

    Public Class main
    Inherits System.Web.UI.Page

    Protected startApplication As String
    Protected startSession As String
    Protected startRequest As String
    Protected jeton as String

    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
         ' si recuperano le informazioni relative all’applicazione e alla sessione
        jeton=Session.SessionId
        startApplication = Application.Item("startApplication").ToString
        startSession = Session.Item("startSession").ToString
        startRequest = Context.Items("startRequest").ToString
    End Sub

End Class

    Il controller si limita a recuperare le tre informazioni inserite rispettivamente nell'applicazione, nella sessione e nel contesto tramite [global.asax.vb].

    2. un primo client richiede l’URL [http://localhost/aspnet/globalasax1/main.aspx] e ottiene il seguente risultato:

    4.1.3.3. Una panoramica

    Con quanto appreso finora, siamo in grado di tracciare un primo schema esplicativo del funzionamento di un server web e delle applicazioni web che esso supporta:

    Lo schema precedente mostra un server che serve due applicazioni, indicate con A e B, ciascuna con due client. Un server web è in grado di servire più applicazioni web contemporaneamente. Queste sono completamente indipendenti l’una dall’altra. Ci concentreremo sull’applicazione A. L’elaborazione di una richiesta del client-1A all’applicazione A si svolgerà nel modo seguente:

    • il client 1A richiede al server web una risorsa appartenente al dominio dell’applicazione A. Ciò significa che richiede una risorsa URL della forma [http://machine:port/VA/ressource], dove VA è il percorso virtuale dell’applicazione A.
    • Se il server web rileva che si tratta della prima richiesta di una risorsa dell'applicazione A, attiva l'evento [Application_Start] del file [global.asax] dell'applicazione A. Verrà creato un oggetto [ApplicationA] di tipo [HttpApplicationState]. I vari codici dell’applicazione memorizzeranno in questo oggetto dati con ambito [Application] e c.a.d, relativi a tutti gli utenti. L’oggetto [ApplicationA] rimarrà in memoria fino a quando il server web non chiuderà l’applicazione A.
    • se il server web rileva inoltre di avere a che fare con un nuovo client dell'applicazione A, attiverà l'evento [Session_Start] del file [global.asax] dell'applicazione A. Verrà creato un oggetto [Session-1A] di tipo [HttpSessionState]. Questo oggetto consentirà all’applicazione A di memorizzare oggetti con ambito [Session] e c.a.d, ovvero oggetti appartenenti a un cliente specifico. L’oggetto [Session-1A] esisterà fintanto che il cliente 1A effettuerà richieste. Consentirà di monitorare tale cliente. Il server web rileva di avere a che fare con un nuovo cliente in due casi:
      • il client non gli ha inviato un token di sessione nelle intestazioni HTTP della sua richiesta
      • il client gli ha inviato un token di sessione che non esiste (malfunzionamento del client o tentativo di pirateria informatica) o che non esiste più. Un token di sessione scade infatti dopo un certo periodo di inattività del client (20 minuti per impostazione predefinita con IIS). Questo periodo è configurabile.
    • In ogni caso, il server web attiverà l’evento [Application_BeginRequest] del file [global.asax]. Questo evento avvia l’elaborazione di una richiesta del client. È frequente non elaborare questo evento e passare il controllo alla pagina richiesta dal client, che a sua volta elaborerà la richiesta. È anche possibile utilizzare questo evento per analizzare la richiesta, elaborarla e decidere quale pagina inviare in risposta. Utilizzeremo questa tecnica per implementare un’applicazione conforme all’architettura MVC di cui abbiamo parlato.
    • Una volta superato il filtro [global.asax], la richiesta del client viene inoltrata a una pagina .aspx che provvederà a elaborarla. Vedremo in seguito che è possibile far passare la richiesta attraverso un filtro composto da più pagine. L’ultima pagina avrà il compito di inviare la risposta al client. Le pagine possono aggiungere alla richiesta iniziale del cliente le informazioni che hanno calcolato. Possono memorizzare queste informazioni nella collezione Context.Items. Infatti, tutte le pagine coinvolte nell’elaborazione della richiesta di un cliente hanno accesso a questo serbatoio di dati.
    • Il codice delle diverse pagine ha accesso ai bacini di dati costituiti dagli oggetti [ApplicationA], [Session-1A], ... È importante ricordare che il server web gestisce contemporaneamente più clienti per l’applicazione A. Tutti questi clienti hanno accesso all’oggetto [Application A]. Se devono modificare i dati in questo oggetto, è necessario eseguire un’operazione di sincronizzazione tra i client. Ogni client XA ha inoltre accesso al serbatoio di dati [Session-XA]. Poiché quest’ultimo è a lui riservato, non è necessaria alcuna sincronizzazione.
    • Il server web serve contemporaneamente diverse applicazioni web. Non vi è alcuna interferenza tra i client di queste diverse applicazioni.

    Da queste spiegazioni si possono trarre i seguenti punti:

    • in un dato momento, un server web serve più client contemporaneamente. Ciò significa che non attende la fine di una richiesta per elaborarne un’altra. In un istante T, vi sono quindi diverse richieste in fase di elaborazione appartenenti a client diversi per applicazioni diverse. I codici di elaborazione che si svolgono contemporaneamente all’interno del server web vengono talvolta definiti thread di esecuzione.
    • I thread di esecuzione dei client di applicazioni web diverse non interferiscono tra loro. Esiste un isolamento.
    • I thread di esecuzione dei client di una stessa applicazione possono dover condividere dei dati:
      • i thread di esecuzione delle richieste di due clienti diversi (con token di sessione diversi) possono condividere dati tramite l’oggetto [Application].

    4.1.3.6. Sincronizzazione dei client

    Il problema evidenziato nell’applicazione precedente è un classico problema (ma non semplice da risolvere) di accesso esclusivo a una risorsa. Nel nostro caso specifico, occorre fare in modo che due client A e B non possano trovarsi contemporaneamente nella sequenza di codice:

    1. lettura del contatore
    2. incremento del contatore
    3. riscrivere il contatore

    Una sequenza di codice di questo tipo viene definita sequenza critica. Essa richiede la sincronizzazione dei thread chiamati a eseguirla simultaneamente. La piattaforma .NET offre diversi strumenti per garantirla. In questa sede utilizzeremo la classe [Mutex].

    In questa sede utilizzeremo solo i seguenti costruttori e metodi:

    public Mutex()
    crea un oggetto di sincronizzazione M
    public bool WaitOne()
    Il thread T1 che esegue l'operazione M.WaitOne() richiede la proprietà dell'oggetto di sincronizzazione M. Se il mutex M non è detenuto da alcun thread (come avviene inizialmente), viene “assegnato” al thread T1 che lo ha richiesto. Se poco dopo un thread T2 esegue la stessa operazione, verrà bloccato. Infatti, un mutex può appartenere a un solo thread. Verrà sbloccato quando il thread T1 rilascerà il mutex M che detiene. Diversi thread possono quindi rimanere bloccati in attesa del mutex M.
    public void ReleaseMutex()
    Il thread T1, che esegue l’operazione M.ReleaseMutex(), rinuncia al possesso del mutex M. Quando il thread T1 perderà il controllo del processore, il sistema potrà assegnarlo a uno dei thread in attesa del mutex M. Solo uno di essi lo otterrà a sua volta, mentre gli altri in attesa di M rimarranno bloccati

    Un mutex M gestisce l’accesso a una risorsa condivisa R. Un thread richiede la risorsa R tramite M.WaitOne() e la restituisce tramite M.ReleaseMutex(). Una sezione critica di codice che deve essere eseguita da un solo thread alla volta è una risorsa condivisa. La sincronizzazione dell’esecuzione della sezione critica può avvenire in questo modo:

    M.WaitOne()
' solo questo thread può entrare qui
' sezione critica
....
M.ReleaseMutex()

    dove M è un oggetto Mutex. Ovviamente non bisogna mai dimenticare di liberare un Mutex che non serve più, in modo che un altro thread possa a sua volta entrare nella sezione critica; altrimenti i thread in attesa di un mutex mai liberato non avranno mai accesso al processore. Inoltre, occorre evitare la situazione di interblocco (deadlock) in cui due thread si aspettano a vicenda. Consideriamo le seguenti azioni che si susseguono nel tempo:

    • un thread T1 acquisisce il controllo di un mutex M1 per accedere a una risorsa condivisa R1
    • un thread T2 acquisisce il controllo di un mutex M2 per accedere a una risorsa condivisa R2
    • il thread T1 richiede il mutex M2. Viene bloccato.
    • il thread T2 richiede il mutex M1. Viene bloccato.

    In questo caso, i thread T1 e T2 si attendono a vicenda. Questo caso si verifica quando i thread necessitano di due risorse condivise: la risorsa R1 controllata dal mutex M1 e la risorsa R2 controllata dal mutex M2. Una possibile soluzione consiste nel richiedere entrambe le risorse contemporaneamente tramite un unico mutex M. Tuttavia, ciò non è sempre possibile, in particolare se comporta un lungo blocco di una risorsa costosa. Un’altra soluzione consiste nel far sì che un thread in possesso di M1, non potendo ottenere M2, rilasci M1 per evitare il deadlock.

    4.1.3.7. Gestione del token di sessione

    Abbiamo parlato più volte del token di sessione scambiato tra il client e il server web. Ricordiamone il principio:

    • il client effettua una prima richiesta al server. Non invia alcun token di sessione.
    • A causa dell’assenza del token di sessione nella richiesta, il server riconosce un nuovo client e gli assegna un token. A questo token è associato anche un oggetto [Session] che verrà utilizzato per memorizzare le informazioni specifiche di quel client. Il token accompagnerà tutte le richieste di questo cliente. Sarà incluso nelle intestazioni HTTP della risposta inviata alla prima richiesta del cliente.
    • Il cliente ora conosce il proprio token di sessione. Lo invierà nelle intestazioni HTTP di ciascuna delle successive richieste che invierà al server web. Grazie al token, il server potrà recuperare l’oggetto [Session] associato al cliente.

    4.2.1. Il ciclo richiesta-risposta del modello client-server web

    Ricordiamo qui il contesto client-server di un’applicazione web:

    La richiesta di un client per un'applicazione web viene elaborata nel modo seguente:

    1. il client apre una connessione TCP/IP verso una porta P del servizio web del computer M che ospita l’applicazione web
    2. invia su questa connessione una sequenza di righe di testo secondo il protocollo HTTP. Questo insieme di righe costituisce quella che viene definita la richiesta del client. Essa ha la seguente forma:

    Una volta inviata la richiesta, il client attenderà la risposta.

    1. La prima riga delle intestazioni HTTP specifica l’azione richiesta al server web. Può assumere diverse forme:
      1. GET url HTTP/<versione>, dove <versione> è attualmente pari a 1.0 o 1.1. In questo caso, la richiesta non include la parte [Document]
      2. POST url HTTP/<versione>. In questo caso, la richiesta include una parte [Document], che nella maggior parte dei casi è un elenco di informazioni destinate all’applicazione web
      3. PUT url HTTP/<versione>. Il client invia un documento nella parte [Document] e desidera memorizzarlo sul server all'indirizzo url

    Quando il client desidera trasmettere informazioni all’applicazione web a cui si è connesso, dispone principalmente di due modalità:

    • (continua)
      1. la sua richiesta è [GET url_enrichie HTTP/<version>], dove url_enrichie ha la forma [url?param1=val1&param2=val2&...]. Il client trasmette, oltre all’URL, una serie di informazioni nella forma [clé=valeur].
      2. la sua richiesta è [POST url HTTP/<version>]. Nella parte [Document], trasmette informazioni nella stessa forma di prima: [param1=val1&param2=val2&...].
    1. Sul server, l’intera catena di elaborazione della richiesta del client ha accesso a quest’ultima tramite un oggetto globale denominato Request. Il server web ha inserito in questo oggetto l’intera richiesta del client in un formato che vedremo tra poco. L’applicazione interpellata elaborerà questo oggetto e costruirà una risposta per il client. Quest’ultima è disponibile in un oggetto globale denominato Response. Il ruolo dell’applicazione web è quello di costruire un oggetto [Response] a partire dall’oggetto [Request] ricevuto. La catena di elaborazione dispone inoltre degli oggetti globali [Application] e [Session] di cui abbiamo già parlato e che le consentiranno di condividere dati tra clienti diversi (Applicazione) o tra richieste successive dello stesso cliente (Sessione).
    2. L’applicazione invierà la propria risposta al server tramite l’oggetto [Response]. Una volta in rete, tale risposta assumerà la seguente forma: HTTP:

    Una volta inviata questa risposta, il server chiuderà la connessione di rete in ricezione (a meno che il cliente non gli abbia indicato di non farlo).

    1. Il client riceverà la risposta e a sua volta chiuderà la connessione (in fase di trasmissione). Il trattamento di tale risposta dipenderà dal tipo di client. Se si tratta di un browser e il documento ricevuto è un documento HTML, questo verrà visualizzato. Se il client è un programma, la risposta verrà analizzata ed elaborata.
    2. Il fatto che, al termine del ciclo richiesta-risposta, la connessione che collegava il client al server venga chiusa rende il protocollo HTTP un protocollo senza stato. Alla richiesta successiva, il client stabilirà una nuova connessione di rete allo stesso server. Poiché non si tratta più della stessa connessione di rete, il server non ha alcuna possibilità (a livello TCP/IP e HTTP) di collegare questa nuova connessione a una precedente. Sarà il sistema del token di sessione a consentire tale collegamento.

    4.2.2. Recuperare le informazioni trasmesse dal client

    Esaminiamo ora alcune proprietà e metodi dell’oggetto [Request] che consentono al codice dell’applicazione di accedere alla richiesta del client e quindi alle informazioni da esso trasmesse. L’oggetto [Request] è di tipo [HttpRequest]:

    Questa classe presenta numerose proprietà e metodi. Ci interessano le proprietà HttpMethod, QueryString, Form e Params, che ci consentiranno di accedere agli elementi della stringa di informazioni [param1=val1&param2=val2&...].

    HttpMethod as String
    metodi di richiesta del client: GET, POST, HEAD, ...
    QueryString as NameValueCollection
    raccolta degli elementi della stringa di richiesta param1=val1&param2=val2&.. della prima riga HTTP [méthode]?param1=val1&param2=val2&... dove [méthode] può essere GET, POST, HEAD.
    Form as NameValueCollection
    raccolta degli elementi della stringa di query param1=val1&param2=val2&... presenti nella parte [Document] della query (metodo POST).
    Params as NameValueCollection
    raggruppa diverse raccolte: QueryString, Form, ServerVariables, Cookies in un'unica raccolta.

Imports System.Collections
Imports System
Imports System.Collections.Specialized

Public Class main
    Inherits System.Web.UI.Page

    Protected infosQueryString As ArrayList
    Protected WithEvents lstQueryString As System.Web.UI.WebControls.ListBox
    Protected WithEvents lstForm As System.Web.UI.WebControls.ListBox
    Protected infosForm As ArrayList

    Private Sub Page_Init(ByVal sender As Object, ByVal e As System.EventArgs) Handles MyBase.Init
        ' si memorizza la richiesta del client in request.txt nella cartella dell'applicazione
        Dim requestFileName As String = Me.MapPath(Me.TemplateSourceDirectory) + "\request.txt"
        Me.Request.SaveAs(requestFileName, True)
    End Sub

    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
        ' si recupera l'intera raccolta di informazioni da QueryString
        infosQueryString = getValeurs(Request.QueryString)
        lstQueryString.DataSource = infosQueryString
        lstQueryString.DataBind()
        infosForm = getValeurs(Request.Form)
        lstForm.DataSource = infosForm
        lstForm.DataBind()
    End Sub

    Private Function getValeurs(ByRef data As NameValueCollection) As ArrayList
        ' inizialmente un elenco di informazioni vuoto
        Dim infos As New ArrayList
        ' si recuperano le chiavi della raccolta
        Dim clés() As String = data.AllKeys
        ' si scorre l'array delle chiavi
        Dim valeurs() As String
        For Each clé As String In clés
            ' valori associati alla chiave
            valeurs = data.GetValues(clé)
            ' un solo valore?
            If valeurs.Length = 1 Then
                infos.Add(clé + "=" + valeurs(0))
            Else
                ' più valori
                For ivalue As Integer = 0 To valeurs.Length - 1
                    infos.Add(clé + "(" + ivalue.ToString + ")=" + valeurs(ivalue))
                Next
            End If
        Next
        ' si restituisce il risultato
        Return infos
    End Function
End Class

    I punti salienti di questo codice sono i seguenti:

    • in [Form_Load] la pagina recupera le due collezioni [QueryString] e [Form]. Utilizza una funzione [getValeurs] per inserire il contenuto di queste due collezioni in due oggetti di tipo [ArrayList] che conterranno stringhe di caratteri del tipo [clé=valeur] se la chiave della collezione è associata a un unico valore o [clé(i)=valeur] se la chiave è associata a più valori.
    • Ciascuno degli oggetti [ArrayList] viene quindi associato a uno degli oggetti [ListBox] della pagina di presentazione tramite due istruzioni:
      • [ListBox.DataSource=ArrayList] e [ListBox.DataBind]. Quest’ultima istruzione trasferisce gli elementi di [DataSource] nella collezione [Items] dell’oggetto [ListBox]

    si noti che nessuno dei due oggetti [ListBox] viene creato esplicitamente da un'operazione [New]. Se ne deduce che, in presenza del tag <asp:listbox id="xx">...<asp:listbox/>, il server web crea autonomamente l’oggetto [ListBox] a cui fa riferimento l’attributo [id] del tag.

    • La funzione [getValeurs] utilizza l’oggetto di tipo [NameValueCollection] che le viene passato come parametro per produrre un risultato di tipo [ArrayList].

    4.3. Implementazione di un’architettura MVC

    4.3.1. Il concetto

    Concludiamo questo lungo capitolo con l’implementazione di un’applicazione costruita secondo il modello MVC (Model-View-Controller). Un’applicazione web strutturata secondo questo modello si presenta così:

    • il client invia le sue richieste a un'entità specifica dell'applicazione chiamata controller
    • il controller analizza la richiesta del client e ne provvede all’esecuzione. A tal fine si avvale di classi che raggruppano la logica di business dell’applicazione e delle classi di accesso ai dati.
    • a seconda del risultato dell’esecuzione della richiesta, il controller decide di inviare una determinata pagina come risposta al client

    Nel nostro modello, tutte le richieste passano attraverso un unico controller che funge da direttore d’orchestra dell’intera applicazione web. Il vantaggio di questo modello è che nel controller è possibile raggruppare tutto ciò che deve essere eseguito prima di ogni richiesta. Supponiamo, ad esempio, che l’applicazione richieda un’autenticazione. Questa viene effettuata una sola volta. Una volta completata con successo, l’applicazione inserirà nella sessione le informazioni relative all’utente che si è appena autenticato. Poiché un client può richiamare direttamente una pagina dell’applicazione senza autenticarsi, ogni pagina dovrà quindi verificare nella sessione che l’autenticazione sia stata effettivamente completata. Se tutte le richieste passano attraverso un unico controller, sarà quest’ultimo a svolgere tale compito. Le pagine a cui la richiesta verrà eventualmente inoltrata non dovranno occuparsene.

    4.3.2. Gestire un'applicazione MVC senza sessione

    Da quanto visto finora, si potrebbe pensare che il file [global.asax] possa svolgere il ruolo di controller. Infatti, sappiamo che tutte le richieste passano attraverso di esso. È quindi nella posizione ideale per controllare tutto. L’applicazione che segue lo utilizza a questo scopo. Il suo percorso virtuale sarà [http://localhost/mvc1/main.aspx]. Per indicare ciò che desidera, il client aggiungerà all’URL un parametro action=valore. A seconda del valore del parametro [action], il controller [global.asax] indirizzerà la richiesta verso una pagina specifica:

    1. [main.aspx] se il parametro action non è definito o se action=main
    2. [action1.aspx] se action=action1
    3. [inconnu.aspx] se `action` non rientra nei casi 1 e 2

    Le pagine [main.aspx, action1.aspx, inconnu.aspx] si limitano a visualizzare il valore di [action] che ne ha determinato la visualizzazione. Di seguito elenchiamo gli otto file di questa applicazione e li commentiamo quando necessario:

    [global.asax]

    <%@ Application src="Global.asax.vb" Inherits="Global" %>

Imports System
Imports System.Web
Imports System.Web.SessionState

Public Class Global
    Inherits System.Web.HttpApplication

    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' si recupera l'azione da eseguire
        Dim action As String
        If Request.QueryString("action") Is Nothing Then
            action = "main"
        Else
            action = Request.QueryString("action").ToString.ToLower
        End If
        ' si inserisce l'azione nel contesto della richiesta
        Context.Items("action") = action
        ' si esegue l'azione
        Select Case action
            Case "main"
                Server.Transfer("main.aspx", True)
            Case "action1"
                Server.Transfer("action1.aspx", True)
            Case Else
                Server.Transfer("inconnu.aspx", True)
        End Select
    End Sub
End Class

    Punti da tenere presenti:

    • intercettiamo tutte le richieste del client nella procedura [Application_BeginRequest], che viene eseguita automaticamente all’avvio di ogni nuova richiesta inviata all’applicazione.
    • In questa procedura, abbiamo accesso all’oggetto [Request], che rappresenta la richiesta HTTP del client. Poiché ci aspettiamo un URL della forma [http://localhost/mvc1/main.aspx?action=xx], cerchiamo una chiave [action] nella collezione [Request.QueryString]. Se non è presente, impostiamo per impostazione predefinita l’azione pari a «main».
    • Il valore del parametro [action] viene inserito nell’oggetto [Context]. Come gli oggetti [Application, Session, Request, Response, Server], questo oggetto è globale e accessibile da qualsiasi codice. Questo oggetto viene passato da una pagina all’altra se la richiesta viene elaborata da più pagine, come avverrà in questo caso. Viene eliminato non appena la risposta è stata inviata al cliente. La sua durata è quindi pari a quella dell’elaborazione della richiesta.
    • A seconda del valore del parametro [action], la richiesta viene inoltrata alla pagina appropriata. A tal fine si utilizza l’oggetto globale [Server] che, grazie al suo metodo, consente di trasferire la richiesta corrente a un’altra pagina. Il suo primo parametro è il nome della pagina di destinazione, il secondo è un valore booleano che indica se si devono trasferire o meno alla pagina di destinazione le collezioni [QueryString] e [Form]. In questo caso, la risposta è sì.

    4.3.3. Gestire un'applicazione MVC con sessione

    Nella maggior parte dei casi, le diverse richieste di un client per un'applicazione devono condividere delle informazioni. Abbiamo visto una possibile soluzione a questo problema: memorizzare le informazioni da condividere nell'oggetto [Session] della richiesta. Questo oggetto è infatti condiviso da tutte le richieste ed è in grado di memorizzare informazioni nella forma (chiave, valore), dove la chiave è di tipo [String] e il valore è di qualsiasi tipo derivato da [Object].

    Nell’esempio precedente, le diverse pagine associate alle diverse azioni venivano richiamate nella procedura [Application_BeginRequest] del file [global.asax.vb]:

    
    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' si recupera l'azione da eseguire
        Dim action As String
        If Request.QueryString("action") Is Nothing Then
            action = "main"
        Else
            action = Request.QueryString("action").ToString.ToLower
        End If
        ' si inserisce l'azione nel contesto della richiesta
        Context.Items("action") = action
        ' si esegue l'azione
        Select Case action
            Case "main"
                Server.Transfer("main.aspx", True)
            Case "action1"
                Server.Transfer("action1.aspx", True)
            Case Else
                Server.Transfer("inconnu.aspx", True)
        End Select
    End Sub

    Si è riscontrato che nella procedura [Application_BeginRequest] l'oggetto [Session] non è accessibile. Lo stesso vale per la pagina a cui viene trasferita l'esecuzione. Pertanto, questo modello non è utilizzabile per un'applicazione con sessione. È possibile assegnare il ruolo di controller a qualsiasi pagina, ad esempio [default.aspx]. Public Class controleur
    Inherits System.Web.UI.Page

    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
        ' si recupera l'azione da eseguire
        Dim action As String
        If Request.QueryString("action") Is Nothing Then
            action = "main"
        Else
            action = Request.QueryString("action").ToString.ToLower
        End If

        ' si inserisce l'azione nel contesto della richiesta
        Context.Items("action") = action
        ' si recupera l'azione precedente, se esiste
        Context.Items("actionPrec") = Session.Item("actionPrec")
        If Context.Items("actionPrec") Is Nothing Then Context.Items("actionPrec") = ""
        ' si memorizza l'azione corrente nella sessione
        Session.Item("actionPrec") = action

        ' si esegue l'azione
        Select Case action
            Case "main"
                Server.Transfer("main.aspx", True)
            Case "action1"
                Server.Transfer("action1.aspx", True)
            Case Else
                Server.Transfer("inconnu.aspx", True)
        End Select
    End Sub
End Class
